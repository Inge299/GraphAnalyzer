# GraphAnalyzer

GraphAnalyzer — настольное/локальное веб-приложение для загрузки проектных данных, построения графов, запуска аналитических плагинов и управления доменной моделью графа.

Проект сейчас уже опирается на единый подход:

- **вывод на граф** делается через плагины;
- **импорт форматов данных** переводится в import-плагины;
- **типы вершин и связей** настраиваются через доменную модель;
- **метаданные** можно экспортировать и импортировать как пакет настроек.

## Что уже умеет система

### 1. Проекты и артефакты

- проекты;
- графовые артефакты;
- console-артефакты;
- производные графы и обновление графа проекта по загруженным данным.

### 2. Данные проекта

Экран `Данные проекта` позволяет:

- выбирать файлы;
- видеть, какой import-плагин будет применён к каждому файлу;
- при необходимости **переопределить выбор import-плагина вручную** до запуска загрузки;
- загружать данные в проект;
- очищать проектные данные;
- смотреть статистику;
- обогащать справочник БС по адресам из данных проекта.

### 3. Справочник базовых станций

Есть отдельный сервисный экран для:

- загрузки справочника БС;
- просмотра статистики справочника;
- использования справочника в проектных сценариях.

### 4. Типы графа

Есть редактор доменной модели графа:

- типы вершин;
- типы связей;
- допустимые пары типов;
- визуальные параметры;
- связь типа связи с `plugin_id`;
- управление показом в меню.

### 5. Плагины импорта

Есть отдельный административный раздел для import-плагинов:

- список доступных import-плагинов;
- редактирование названия;
- редактирование описания;
- редактирование приоритета;
- включение/выключение плагина.

### 6. Метаданные

Есть отдельный административный раздел `Метаданные`:

- **экспорт метаданных** в JSON;
- **импорт метаданных** из JSON.

Сейчас в пакет метаданных входят:

- доменная модель графа;
- реестр import-плагинов.

## Архитектурный подход

### Графовые/аналитические плагины

Любое осмысленное изменение графа должно происходить через плагин.

Примеры рабочих graph/analysis-плагинов:

- `Пользователь <-> MSISDN`
- `IP <-> MSISDN`
- `MSISDN <-> Устройство`
- `Записан как...`
- `Адресная книга`
- `Связи абонента`
- `Абонентский номер`

Важно:

- **логика** плагина живёт в Python;
- **метаданные** плагина и его место в UI настраиваются через доменную модель и витрину плагинов.

### Import-плагины

Импорт форматов данных переводится на такой же стандарт:

- каждый поддерживаемый формат оформляется как **отдельный import-плагин**;
- import-плагин умеет:
  - распознать формат;
  - запустить импорт;
  - вернуть результат и статистику.

Это даёт единый сценарий:

1. пользователь показывает файлы;
2. система определяет, какой import-плагин применить;
3. при необходимости пользователь меняет выбор;
4. выбранный import-плагин выполняет загрузку.

## Текущие import-плагины

Сейчас заведены такие import-плагины:

- `nodex_archive_bundle`
- `nodex_identity_facts`
- `nodex_traffic_geo`

Они хранятся как кодовая логика на backend и имеют редактируемые метаданные.

## Распознавание форматов

Система уже умеет:

- распознавать отдельные CSV по имени и заголовкам;
- распознавать ZIP-архивы по **внутренним файлам и внутренним CSV-заголовкам**, а не только по имени архива;
- применять import-плагин **к каждому файлу отдельно**;
- разбивать пакет загрузки на группы файлов по import-плагинам.

## Что сейчас можно менять без переписывания кода

Без изменения логики программы уже можно:

- менять названия import-плагинов;
- менять описания import-плагинов;
- менять приоритеты распознавания;
- включать и выключать import-плагины;
- редактировать типы вершин;
- редактировать типы связей;
- менять визуал типов;
- менять меню и подписи для связей;
- экспортировать и импортировать пакет метаданных.

## Что пока остаётся кодовым

Пока всё ещё требует Python-кода:

- новый алгоритм импорта;
- новый format recognizer;
- новый graph/analysis plugin;
- новая сложная логика построения графа.

То есть метаданные уже конфигурируемы, а **исполняемая логика** пока кодовая.

## Как запускать

Обычный локальный цикл разработки:

1. backend через Docker Compose;
2. frontend локально;
3. проверка frontend:

```powershell
npm.cmd run typecheck
```

4. проверка python-модулей:

```powershell
py -m py_compile app\services\project_data_import_plugins.py app\services\project_data_service.py app\api\routes\project_data.py
```

## Куда двигаться дальше

Самые логичные следующие шаги:

1. перевести **каждый новый формат данных** в отдельный import-плагин;
2. держать **каждый новый сценарий анализа/расширения графа** как отдельный graph-plugin;
3. постепенно расширять пакет метаданных;
4. при необходимости сделать следующий уровень — декларативные плагины для простых случаев, не ломая кодовую модель.

## Принцип проекта

Коротко:

- всё, что **исполняется**, лучше делать как плагин;
- всё, что **настраивается**, лучше держать в метаданных;
- UI должен показывать не техническую внутренность, а понятный сценарий работы пользователя.
